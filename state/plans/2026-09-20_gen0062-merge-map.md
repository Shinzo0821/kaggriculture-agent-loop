## 1. 移植する payload（gen0051 → gen0059 の farmer ゾーン機構）

1. `n_zones = max(n_hands, hands_target(day, expand)) + 1`（旧 `, 1` は削除。P1-3 の off-by-one 修正込み）
2. `farmer_zone` = シェッド最短距離が最小の区画 / `hand_zone` / `unit_zid` / `zone_pos` の導入
3. `_owner_can_come` の `owner >= len(hand_pos)` → `zone_pos[owner] is None`、`hand_pos[owner]` → `zone_pos[owner]`
4. `zid = unit_zid[ui]`（旧 `zid = ui - 1`）
5. `farmer_shed = (_ui == 0 and (need == "SHEDOP" or op[0] == "PLACE"))` と、それを `zone_only` の 2 経路
   （`need == "SHEDOP"` 分岐 と `zone_of.get((x,y)) != _zid` 分岐）で通す例外
6. `eff = min(pri, 0.85) if farmer_shed else pri`
7. **`crit` の 3 段化**: `0 if pri in LOSS_PRIS else (1 if farmer_shed else 2)`
8. `rescue_all` と、farmer の一括 PICKUP への `hour >= 2` 条件・`cap` の分岐

## 2. gen0058 のガードを戻す位置（**合流の本体**）

gen0059 が消した 2 つを、gen0059 の構造の上に戻す。

**(G1) 到達可能性ゲート**（`d` を計算した直後、`lay = pri_layer(eff)` の前）:
```python
# 親が gen0060 なので carve-out は FIX0030 後の形（緊急 FEED のみ免除）。
# [訂正 2026-09-20 c3] 下の旧 `pri not in LOSS_PRIS` は gen0058 の形で、実装はこちら:
if (day < FINAL_DAY and not (pri == 0.0 and op[0] == "FEED")
        and d + 1 > HOURS_PER_DAY - hour):
    continue
```
→ **設計判断（c2 が解決。c3 は蒸し返さない）: `farmer_shed` を carve-out に足さない ＝ ゲートは全 todo に効かせる。**
根拠はエンジン規則:
- `_end_of_day` は `_drop_inventories_to_shed(private, shed_cap)` を呼ぶ（`kaggriculture.py:875`）＝
  **携行中の動物は日の終わりにシェッドへ戻る。** よって「今日中に着けない PLACE」を今日選ばないことの
  損失は**ほぼ**ゼロで、翌朝シェッドから設置し直せる（親 gen0022 のコメント「シェッド泊で翌朝設置」と同じ経済）。
  **[訂正 2026-09-20 c3・Codex gen0062#P1-3] 「損失はゼロ」は言い過ぎだった。** `_drop_inventories_to_shed` は
  `room = max(0, capacity - current)` / `take = min(n, room)` のあと `del inv[item]` で**入り切らない分を捨てる**
  （README「Anything that doesn't fit is discarded — overflow is lost」）。シェッドが満杯の日に動物を携行したまま
  EOD を迎えると**動物が消える**。実測（gen0062 スモーク 3 seed）: `shed + carried` の最大は 120/115/105 で
  容量 100 を超える瞬間はあるが、**EOD に動物を携行していた日は 0 件**で 3 seed とも d8 に 12 頭到達。
  ＝**正確には「通常は翌朝シェッドへ戻るが、容量超過時は破棄されうる。3 smoke では未発火」**までしか言えない
  （Codex gen0062 round2 の言い直しを採用）。50 シード評価で invariant として見る（EXP0062）。
- そもそも PLACE には既に `hour >= 18` の打ち切りがある（`main.py:890`）＝「遅い設置はその日の給餌・世話が
  間に合わない」という**同じ向きの設計**が親に入っている。到達可能性ゲートはその一般化であって新しい方針ではない。
- gen0059 の「動物が 8 頭で止まった」事故は**時間ゲートではなく、PLACE が `zone_only` から永久に締め出されて
  いたこと**が原因（`farmer_shed` 例外はそれを直すためのもの）。carve-out の話とは別の穴。

ただし carve-out を置かない以上、**スモークの `micro_audit` で動物頭数（親 12 頭）を必ず確認する**
（この推論が外れていれば頭数に出る）。理由は EXP0062 に上の 3 点で書く。

**(G2) FEED/CARE の最寄り判定の対象集合を揃えるガード**（`ds` を作るループの中、`zi = unit_zid[i]` の前）:
```python
if (day < FINAL_DAY
        and abs(px - x) + abs(py - y) + 1 > HOURS_PER_DAY - hour):
    continue
```
gen0058 の意図は「保護の対象集合と最寄り判定の対象集合を一致させる」。
**[訂正 2026-09-20 c3] 「(G1) と (G2) を同じ carve-out に揃えること」は誤り。** 実装は
**G1 = 緊急 FEED のみ免除 / G2 = 免除なし**で、この非対称は意図的（下の §4-2）。
なお (G2) は `i == 0`（farmer）にも効くが、gen0059 では farmer が区画を持つので
直後の `if i == 0:` の FIX0005 分岐との相互作用を読み直す必要がある。

## 3. 親が gen0060 になった場合に**追加で**生じる衝突（gen0060 が `gate.pass` のときだけ）

gen0060 は `_owner_can_come` を書き換え、`_zone_backlog_doable()` を新設した。
**この新設関数は「ゾーン番号 == hand の番号」を 3 箇所で仮定している**ので、farmer が区画を持つと全部壊れる:

| 行 | 現状（gen0060） | 合流後に必要な形 |
| --- | --- | --- |
| `if z is None or z >= len(hand_pos): continue` | 未雇用ゾーンの除外 | `zone_pos[z] is None` で判定（farmer_zone は常に非 None） |
| `_oinv = invs[z + 1]` | ゾーン z の所有者 = unit z+1 | ゾーン → unit の逆引き（`unit_zid` の逆写像）で unit index を引く |
| `px, py = hand_pos[z]` | 所有者の現在位置 | `zone_pos[z]` |

さらに `_rank()` は `eval_todos` の `key` を再現する関数なので、**`crit` の 3 段化（§1-7）を `_rank` にも
反映しないと「所有者の順位付けの再現」が嘘になる**。hands については 1→2 の付け替えだけなので層内順序は
不変だが、**所有者が farmer の区画では `farmer_shed`（PLACE）の crit=1 が効く**ので再現が崩れる。
`_zone_backlog_doable` は `need` が `UNIT*` / `SHEDOP` の todo しか除外しない。**PLACE の todo は
`todos.append((2.4, x, y, ["PLACE", a], a))`（`main.py:895`）＝ need が動物名・座標は実タイルなので
`zone_of` に載り、巡回に入る。** しかも同関数の在庫フィルタ `if _need in ANIMALS and _oinv.get(_need,0) <= 0`
は「そのゾーンの所有者が動物を携行しているか」で切るので、**所有者が farmer の区画では
（動物を運ぶのはまさに farmer なので）このフィルタを通過し、crit=1 の PLACE が crit=1 として
再現されないまま巡回順に混ざる** —— **ここが合流固有の穴**（親が gen0060 のときのみ）。

## 4. Codex レビューに足す観点（計画の「2 機構の相互作用」を具体化したもの）

1. farmer は (G1) のゲートを通るか。**c2 の判断は「farmer_shed を carve-out にしない」**（§2 の 3 根拠）。
   この判断の反証（携行動物が翌朝シェッドに戻らない経路・頭数が 12 に届かない seed）を探させる。
2. (G1) と (G2) の carve-out が一致しているか（不一致 = gen0058 が塞いだ穴の再発）。
   **[訂正 2026-09-20 c3] 親が gen0060 なので carve-out は同一ではない。** G1 は FIX0030 で
   `not (pri == 0.0 and op[0] == "FEED")`（緊急 FEED のみ免除）、G2 は**免除なし**。
   **この非対称は意図的**（Codex gen0062#P2 も同意）: G1 の免除は「ゲートを掛けると割当がずれて給餌が
   落ちた」という経験的 fallback、G2 が求めているのは「**今日実行できるユニットの中での最寄り**」。
   免除を足しても `dmin` はほとんど動かない（ゲートは距離だけで決まるので降りるユニットは通るユニットより
   必ず遠い）が、**全ユニットが到達不能な盤面では `ds` が空 → `dmin=None` → 最寄り判定が無効**になる。
   「誰も来られないなら誰が取ってもよい」を保つために免除は入れない。
   （**c3 の当初の説明「到達不能な近いユニットが dmin を作り遠いユニットを弾く」は誤り** —— ゲートは
   距離の単調関数なので、その組み合わせは成立しない。Codex gen0062 round2 の指摘で訂正した。）
   gen0062 のコード側にこの注記を書いた。
3. `_rank` の `crit` が `eval_todos` の `crit` と同じ 3 段になっているか（親 gen0060 のときのみ）。
4. `_zone_backlog_doable` の 3 箇所のゾーン↔hand 仮定が `zone_pos` / `unit_zid` 逆写像に置き換わっているか。
5. farmer のゾーン所有（gen0059）と所有権のバックログ解除（gen0060）が**二重に同じ仕事を奪い合わないか**
   —— farmer は「自ゾーンの所有者」になったので、他ユニットの解放対象にもなる。
6. **日替わりの farmer 位置リセット**（Discussion 741907・エンジン `kaggriculture.py` L875-882）:
   `zone_pos[farmer_zone]` は毎ターン観測から読んでいるか（固定値を持ち回っていないか）。
7. `hands_target` が 0 を返す日の `n_zones`（P1-3 の off-by-one）が合流後も正しいか。

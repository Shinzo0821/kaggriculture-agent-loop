## 1-4 だけの版は「自分も大きく損する削り」だった（`too_good` が働いた例）

計画 §5 の 4 点だけを入れた版を 24 シードで測ると、資金差 **+$8,206 [CI +4,898, +11,514]** が出て
**`too_good` フラグが立った**（閾値 $8,000）。中身は、労働効率が上がって出荷量が増え、
共有市場の価格を潰した結果だった。

**注意（枠組みの訂正）**: 相手の稼ぎを削ること自体は**このゲームでは正当かつ有効**である
（勝敗は最終資金の大小で決まるので目的関数は差であり、共有市場で自分が売れば相手の売値が
下がるのはエンジンの規則）。当初ここに「資金の伸びの正体は生産ではなく市場破壊だった＝不純」と
書いたのは**誤り**（`knowledge/analysis/2026-09-05_denial-vs-production.md`）。
1-4 版を採らなかった理由は削りそのものではなく、**自分の絶対額まで大きく落ちる型**だったこと
（s7 で $73k → $36k）と、後半 slope が −381 と負だったこと。

3 つの警告が同時に出ていた: (1) `too_good`、(2) 後半 slope が負、

1-4 版を採らなかった理由は **自分の絶対額が落ちること**（s7 で $73k → $36k）だけ。
自分の資金が薄いと再投資（土地・動物・種）が回らず翌日以降の生産能力そのものが落ちる。
後半 slope −381 はその現れ。

（当初ここに「勝敗が飽和した相手への削りは順位に効かないので前進と数えるな」と書いたが**撤回**。
その理屈は生産にも同じだけ当てはまる — 強帯戦で自分の資金が +$7,588 増えても反転した試合は 0 戦。
削り固有の問題ではなくプール飽和の問題だった。さらに `paired_delta` は自分の資金しか見ていないので、
**ゲートはそもそも削りを一切カウントしていない**。詳細は
`knowledge/analysis/2026-09-05_denial-vs-production.md`。）

### なぜそうなったか（エンジンの規則）

`kaggriculture.py` 192-206 / 735-747:
- 価格 = `base − amp × f(在庫 − I0)`。**在庫は売却で増え、町の消費でしか減らない**（回復しない）。
- `amp` は「**T 個売ると価格が target × base だけ動く**」ように決まっている。
  MILK は `T=122 / above_target=1.60`、STRAWBERRY は `T=100 / 1.60`、WOOL は `T=105 / 3.20`。
  → **100 個ちょっと売っただけで床($1)に張り付く。**
- 旧の売却規則は「価格が `SELL_FLOORS`（base×0.6）以上なら**全量売り**」。これは
  **旧スループット前提の tuned な規則**で、労働効率が上がると自分でグラットを起こす。

### 直し方（変更 5）

在庫予算（`I0 + GLUT_SLACK − 現在庫`）を**常に**適用する。終盤の清算（`DUMP_DAY`）と
シェッド溢れ（`SHED_DUMP`）だけ例外。予算はエンジンの価格モデルから導けるので `derived`。
これで労働指標を保ったまま**自分の絶対額が上がった**（$51.4k/$35.7k/$43.4k →
$56.9k/$62.5k/$67.7k）。相手の資金も戻るが、それは目的ではなく結果。

**採用版でも削りは残っており、それでよい**。50 シードの内訳（勝敗を決めるのはマージン）:

| | 全プール | 強帯のみ |

| 自分の資金の差（ゲートが見ている値） | +$8,974 | +$7,588 |
| 相手の資金の差（ゲートは見ていない） | −$5,095 | −$6,954 |
| **マージンの差** | **+$14,069** | **+$14,542** |

**旧ゲートは削りを一切カウントしなかったので、gen0026 は旧ゲートが言うより 1.6-1.9 倍良い。**
→ この実測を根拠に、2026-09-05 夕に**昇格ゲートの資金基準をマージンに変更した**

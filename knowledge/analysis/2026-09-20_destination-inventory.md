- 日付: 2026-09-20（夜 cycle2 相当）／ 担当: Analyst
- 対象: 王者 **gen0058** と **gen0059** × 相手 2 体（`agents/sparring/dmitriigluzdov_7turn` / `agents/gen0045`）× seed 7 / 42 / 5000 = **12 戦**
- リプレイ: `records/di{58,59}_{7turn,gen0045}_s{7,42,5000}_replay.json`（本解析で新規生成。`records/` は gitignore）

- **資金・勝敗には一切言及しない。** 12 戦はスモーク帯（検出限界: 方向判断 24 シード）であり、本メモが使うのは決定論的に出る**行動会計と盤面の件数だけ**である。

## なぜ測ったか

2026-09-19 夜の 3 実験がすべて同じ形を示した（`state/STATUS.md` cycle7 / cycle8）:
futile MOVE を消すと 100% が PASS に化け、PASS を消すと 2/3 が通勤 MOVE に化け、

本メモはその「行き先の在庫」を盤面から数える。

## 1. 定義

すべて `observation` から曖昧さなく決まる。エージェントの内部ログ・自己申告には依存しない。

- **1 unit-hour** = 1 ユニット（farmer + hands）の 1 時間の行動。
  「d 日 h 時の行動」は `steps[d*24+h+1]["action"]`、盤面は `steps[d*24+h]["observation"]`（`micro_audit.py` と同じ）。
- **遊休 unit-hour** = 行動が `PASS` または `MOVE`(NORTH/SOUTH/EAST/WEST) の unit-hour。
  すべての MOVE は `2026-09-19_move-budget.py` の「MOVE 区間」に属するので、
  指示の「PASS の unit-hour ＋ 通勤 MOVE の unit-hour」＝「生産行動でない unit-hour」と一致する。
  内訳は PASS / MOVE 別にも出した。**d10-27 では総 unit-hour の 60.0-60.4% が遊休である。**
- **到達圏内** = manhattan 距離 d の仕事について `d + 1 <= 24 - hour`。
  時刻 hour のユニットは h..23 の `24 - hour` 手打てるので、歩き d 手 + 実行 1 手が収まる
  （`2026-09-19_move-budget.py` の cycle6 修正と同式。agent 側の `_owner_can_come` と同じ式）。
- **誰も手を付けていない** = その (day, hour) に、そのタイル上で非 MOVE・非 PASS の行動が
  打たれていない（既存スクリプトと同じ `busy` セット）。
- **持ち物の実行可能性**: FEED は WHEAT を、FERTILIZE は FERTILIZER を、PLACE は動物を
  そのユニットが持っていなければ「そのユニットにできる仕事」ではないので数えない。
- **行き先の帰属（fate）**（本メモの追加）: 数えた仕事は、その日のうちに誰が実行したかで 3 分割する。
  `self`（その遊休ユニット自身が同じ日に同じ op を実行 ＝ 今まさに歩いて向かっている先）/
  `other`（同じ日に別のユニットが実行）/ `never`（その日は誰も実行しなかった）。

  間に合わず確定枯れ）。9/19 の `move-budget-decomposition.md` §7 が既に「閾値の微調整」として却下した論点。
- HARVEST_ANIMAL 14,489 は **意図的な収穫バンク**（gen0022 の出荷制御。価格床以下では動物上に据え置く）。
- FERTILIZABLE 38,862 は **施肥がイチゴの生産日（age 9/11/13/15）にしか効かない**というエンジン規則。

**骨格の穴と呼べるのは ★ を付けた 3 項目だけ**で、d10-27 の (ii) 異なり数のうち
**2,895 + 63 = 2,958 件（1.9%）**（＋ 収穫バンク 14,489 を「戦術判断」として別扱いするなら加算）。
とくに **PLANTABLE「計画が予約中 / 窓が閉じている」18,413 件は d0-9 に偏っており**
（d10-27 では 2,895 件 = 2.0%）、これは序盤に計画表が先の窓のためにタイルを押さえている状態で、
`FALLBACK_CYCLE_DAYS` の論点（9/19 に実測で否定済み）と同じ場所を指している。

## 5. 結論

### **厚い**

事前登録の基準は「d10-27 の帯で、遊休 1 unit-hour あたり (i) の件数が **≥ 0.5 件 = 厚い** /
**< 0.2 件 = 薄い** / **0.2-0.5 = 判定保留**」。

**測定値: d10-27 で (i)/遊休 = 42.95 件/unit-hour**（遊休 37,421 unit-hour に対し (i) 1,607,231 件）。
**基準の「厚い」ライン 0.5 の 86 倍**である。base kind のみでも 38.85、
fate:self を除いた strict でも 40.13 で、どの数え方でも「厚い」を大きく上回る。
seed ブレは同一組み合わせ 3 seed で ±0.3、世代間でも 40.96（gen0059）〜44.93（gen0058）で、
**基準をまたぐ可能性は一切ない。**

### 事前登録の基準そのものへの指摘（結論は動かさない）

**この基準は事実上「厚い」以外を返せなかった。** 理由は定義から出る:
到達圏の式 `d + 1 <= 24 - hour` は朝の時刻ではほぼ盤面全体を含む（h6 なら d ≤ 17 ＝ 10×10 盤の全域）。
したがって (i) の件数は「盤上で今 todo になっている仕事の総数」に漸近し、
「遊休 1 unit-hour あたり 0.5 件」＝「盤上に todo が 1 件もほぼ無い」という、
**最終日以外では起こりえない状態**を薄さの条件にしていた。
実際 d28-29 だけは 9.83（PASS に限れば 4.36）まで落ちており、**この基準が識別できるのは
「最終日にはもう仕事が無い」という cycle8 が既に知っていた事実だけ**である。
今後この量を指標にするなら、**分母と重複を揃えた補助 B（容量マッチ）か補助 D（日単位の純余剰）を使うべき**
（本メモはどちらも同時に出した。事後に基準を差し替えてはいないが、次回の事前登録はこちらで置くべきである）。

### より厳しい数え方での値（記録として）

| 数え方 | d10-27 の値 | 同じ 0.2 / 0.5 のスケールに当てると |
| --- | --- | --- |
| 事前登録（(i)/遊休 uh） | **42.95** | 厚い |
| strict（自分の目的地を除く） | 40.13 | 厚い |
| 容量マッチ充足率（その時間に別々の仕事を渡せた遊休ユニットの割合） | **0.87** | 厚い |
| 日単位の純余剰（(i)&never の異なり数 / 遊休 uh） | **0.12** | （薄い側） |

**この 4 つは矛盾していない。** 3 番目までは「**渡せる仕事はいくらでもある**」を言い、
4 番目は「**そのうち "今日誰もやらない仕事"（＝ 再配分ではなく純増になるもの）は 0.12 件/遊休 uh**」を言う。
fate の内訳がこれを直接裏付ける: **(i) の 66.4% は同じ日のうちに別のユニットが実行しており、
渡す相手を変えても総生産は増えない**。純増になるのは残る 26.5%（日単位の異なり数で 4,523 件、その **73% が PLANT**）。

## 6. これが今後の系統選択に意味すること

1. **労働割当の系統は「頭打ち」ではない。** 遊休 unit-hour の 87% は、その時刻に
   **todo に載っていて・未着手で・到達圏内の、互いに異なる仕事**へ割り当てられた
   （補助 B の最大二部マッチ）。9/19 の 3 実験が「無駄を消しても価値が生まれない」ように見えたのは、
   **行き先が無かったからではなく、消した無駄が最終日（d28-29、充足率 0.53）と
   最終ターン付近に偏っていたから**である。帯を分けると d10-19 は 0.89、d20-27 は 0.84 で、
   **中盤には行き先がある。**
2. **ただし「行き先を変える」だけでは総生産は増えない。** (i) の 2/3 は今日どうせ誰かがやる仕事で、
   割当を変えても実行者が入れ替わるだけ（換金の前倒し分しか残らない）。
   **純増になる行き先は日あたり 20-39 件で、その 73% が PLANT（＝ 埋まらなかった空きタイル）に集中し、
   `LAST_PLANT_DAY = 25` を過ぎた d26 で 2.7 件に崩れる。**
3. **したがって次の一手は「PASS → MOVE への化けを減らす」一般論ではなく、
   `d10-25` の空きタイルを当日中に埋める一点に絞るべき**（9/19 §6-2 の「空きタイルは二重に損をする」と同じ場所）。
   これは `IDEA_POLICY` の「労働割当の構造変更」に収まり、新しい閾値を作らない
   （期限も到達可能性もエンジン規則から出る）。逆に言えば、**この一点を潰したあとに
   労働割当の系統で残る余地は、換金タイミングの前倒しだけ**である。

## 7. 学び（ゲーム構造への還元）

1. **「行き先の在庫」は 2 つの別の量である。** 盤上に todo がある（在庫）ことと、
   その仕事が**今日誰にも実行されない**（純余剰）ことは違う。1 日 24 時間 × ユニット数という
   労働予算がほぼ盤面の仕事量に見合っている以上、**在庫は常に厚く、純余剰だけが希少**になる。
   改善を測るときは在庫ではなく純余剰を分母に置く。
2. **純余剰は締切で作られる。** `LAST_PLANT_DAY = 25` / `LAST_PLANT_HOUR = 20` /
   `LAST_FEED_DAY = 28` / `day < FINAL_DAY` という 4 つの期限が、
   「今日やらないと永久に失われる仕事」と「明日でもよい仕事」を分けている。
   **純余剰の 73% が PLANT なのは、植付だけが "遅れが当日で完結せず盤面の空きとして翌日以降に伝播する" 行動**
   だからである（水やり・給餌はその日のうちに回復不能だが翌日リセットされ、収穫は待てる）。
3. **最終日に行き先が無いのは規則から出る。** `_end_of_day` が hands を捨て farmer を戻す
   （`kaggriculture.py` 879-881）ため d29 h22 以降は換金の手番が無く、
   d28-29 の充足率は 0.53、PASS に限れば (i)/遊休 が 4.36 で全帯最小になる。
   **cycle8 の「FIX0028/FIX0029 が資金に 1 ドルも効かない」は、この帯を触ったことの直接の帰結**であり、
   同じ修正を中盤に当てれば結果は違いうる（帯を分けずに「無駄を消しても意味がない」と一般化してはならない）。
4. **測定器について**: 到達圏の式 `d + 1 <= 24 - hour` は朝ほど盤面全体を含む。
   この式で「件数」を数える指標は**時刻に強く依存する**ので、日帯ではなく時刻で正規化するか、
   容量マッチのように**分母（遊休ユニット数）と重複を揃える**必要がある。
   `control/targets.json` の `micro` に入れるなら候補は
   **「容量マッチ充足率（d10-27）」0.87** か **「日単位の純余剰 / 遊休 uh」0.12** である（基準値の設定は人の判断）。
